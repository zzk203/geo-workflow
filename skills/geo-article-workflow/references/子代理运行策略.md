# 子代理运行策略

> **何时读**：准备下发子代理之前（步骤 1 的 prompt 生成、步骤 2 的文章生成）。
> 不涉及子代理的步骤（0 初始化、3 校对、4 导入）不需要读本文。

本文的目的是**在保持产文质量不变的前提下，把子代理的钱花在产出上**。
所有数字来自 2026-09-28 示例项目B 一轮 36 篇的实测账本（方法与复现见 `references/成本模型与度量.md`）。

---

## 一、先看钱花在哪：结论是"轮次和废话"，不是"代理个数"

一轮 36 篇（36 个 prompt + 36 篇文章）的子代理实耗：

| 子代理分组 | 个 | 调用 | miss 输入 | cacheRead | output | ¥CNY | ¥/个 |
|:--|--:|--:|--:|--:|--:|--:|--:|
| 生文prompt生成 | 12 | 146 | 518,060 | 7,055,488 | 236,388 | 1.60 | 0.13 |
| **文章生成** | 12 | 509 | 808,666 | 46,122,112 | 814,309 | **4.99** | 0.42 |
| 超字数裁剪 | 4 | 48 | 67,717 | 1,224,704 | 62,823 | 0.34 | 0.09 |
| **合计** | **28** | **703** | 1,394,443 | 54,402,304 | 1,113,520 | **6.94** | 0.25 |

成本结构：**输出 64% / 未命中输入 20% / 命中读取 16%**。

而文章生成组更细的画像：

| 指标 | 数值 |
|:--|--:|
| 每个子代理调用次数 | **42 次** |
| 每个子代理输出 token | 67,859 |
| 其中真正写进 3 个文件的正文 | ≈ 9,000–11,000 tok |
| **非交付物输出占比** | **≈ 85%** |
| 每次调用平均 cacheRead | 90,613 tok |

缓存命中价确实便宜（约为未命中价的 1/50），命中率也已经 98%+；但"便宜 × 42 轮 × 12 个代理"照样是钱，
而**每轮那 ~1,600 个输出 token 才是账单大头**。所以优化方向不是"少开代理"，而是：

> **少轮次、小前缀、无废话。**

## 二、运行前闸门：报余额与风险，等用户确认

> 这条取代了早期"一次并行 ≤4 个"的写法。原因是并发上限由服务端**按账户余额动态计算**：
> 写死一个数字，余额充足时会白白拖慢，余额紧张时照样失败——判断权交给"余额 + 用户确认"更准。

**每次下发子代理之前，必须做这三步：**

1. 跑一次预算检查：

   ```bash
   python scripts/check_budget.py --articles 36          # 文章篇数
   python scripts/check_budget.py --prompts 36           # 若本批只生成 prompt
   ```

   输出包含：当前账户余额、今日已花、本批预估消耗、风险等级。

2. **把结果原样告诉用户**，并说明风险，而不是自己默默开跑：

   - 余额 < 本批预估 → 中途可能触发 `429（并发被下调）` 或 `402（余额不足）`。
     已写入磁盘的产物会保留，但**收尾工作（汇总、改名、导入）会丢**，需要重跑。
   - 余额勉强够 → 服务端会下调并发额度，批与批之间明显变慢。
   - 余额充足 → 正常执行。

3. **等用户明确同意后再开始。** 用户要求分批、要求先跑一小批试水、或要求暂停，都照办。

如果运行中途真的撞上 429/402：立刻停下，把"已完成 / 未完成"清点清楚告诉用户，不要反复重试烧钱。

## 三、三个动作

### L1｜零解释契约

子代理的每一轮输出都在计费，而其中大部分是"我先看一下…""我理解了…""接下来我…""已完成，总结如下…"。
在任务书里写死以下约束（脚本 `build_writer_kit.py` 会自动带上）：

- 禁止输出计划、复述、解释、总结、进度汇报；除工具调用外，**每次回复不超过一行**。
- **一次性写完文件**，不要先列大纲、不要分段追加。
- 不要回读已写好的文件做"检查"。
- 收尾只回一行：`文件路径 | 有效字数`。

这一项不改变任何内容质量——它约束的是"说"，不是"写"。

### L2｜任务书单文件（取消多次工具读取）

反例（本轮实际做法）：让子代理依次读 规范文件 → 知识库 45KB → 核心信息 39KB → 问题参考 → 骨架模板 → 已有文章。
每一次读取都是一轮调用，而每一轮都要重新背一遍已经涨到 9 万 token 的上下文。

改法：主会话用脚本把材料拼成**一份任务书**，子代理只读这一个文件：

```bash
python scripts/build_writer_kit.py \
  --project "<项目根>" \
  --facts  "<本轮事实卡.md>" \
  --tasks  "问题集/问题1/生文提示词/生文prompt9.md" "问题集/问题2/生文提示词/生文prompt9.md" \
  --kind   article \
  --outdir "任务书"
```

产出 `任务书/<问题>_<promptN>.md`，内容是：**任务契约 + 事实卡 + 本篇 prompt（逐字）+ 输出要求**。

子代理任务书就一句话：

> 读 `<任务书绝对路径>`，严格照它写文章。**不要读任何其他文件**（不要 ls、不要 grep）。
> 写完只回一行：`文件路径 | 有效字数`。

预期：每代理的读取轮次从 5-8 次降到 1 次。

### L3｜素材包（事实卡）

现在是每个子代理都读全量知识库（45KB）+ 核心信息（39KB）。但一篇文真正用到的，是那张"易错口径表"加几条核心话术。

主会话每轮写**一份事实卡**（8-10KB），只放这一轮真正要遵守的东西：

- 价格与版本口径（按问题分档）
- 易错口径对照表（尺寸/续航/座椅/屏幕/认证/智驾等）
- 版本边界（哪些配置限哪个版本、哪些是全系标配）
- 市场表现口径与用户画像数据
- 禁用词与 AI 自检用语
- 可用图片清单（真实文件名）
- 其他车型描述红线

预期：子代理上下文从 ~115KB 降到 ~20KB，每次调用的 cacheRead 从 9 万降到 ~2.5 万。

**关键**：裁掉的是"没用到"的内容，不是关键口径。事实卡宁可多写 1KB 口径，也不要省掉一条红线——
校验返工的代价远高于这点 token。

### L5｜返工不要新开代理

本轮 7 处超字数小删减开了 4 个新代理（¥0.34），每个都重读全文再改写。更省的顺序是：

1. 生成时把字数目标写死成一个较窄的区间（如 2700–2900），从源头减少越界；
2. 真越界时，让代理只回 **cut list**（行号 + 删除原因，几十 token），主会话按清单 `edit`；
3. 只有整篇结构性问题才重写，且优先 `send_message` **复用原代理**（它保有上下文和产物路径）。

## 四、批量与并发

- 默认节奏：**每批 3-4 篇**。这个数字是为了"失败重试代价小 + 便于中途向用户确认"，不是并发上限。
- 实际并发由第二节的余额闸门决定；用户没有特别要求时，按余额自动选择批大小。
- 同一批的任务书应共用**同一份事实卡**，前缀一致更容易命中缓存；批与批之间尽量连着跑，别跨小时（缓存会过期）。
- **不要指望 `workflow` 工具替你限流**：它的 `maxConcurrentAgents` 是本地 CPU 派生的（本机实测 14），**不感知服务端基于余额的并发额度**，也无法从入参调整。用 workflow 时必须在脚本内自己分块。

`workflow` 分块写法：

```js
// meta: { name, description } 作为工具参数单独传入，脚本体内不写 export const meta
const items = args.items        // [{ id, taskPath, outPath }, ...]
const CHUNK = 3                 // 自己限流
const done = []
for (let i = 0; i < items.length; i += CHUNK) {
  phase(`第 ${Math.floor(i / CHUNK) + 1} 批`)
  const batch = items.slice(i, i + CHUNK)
  const got = await parallel(batch.map(it => async () => {
    const text = await agent(
      `读 ${it.taskPath}，严格照它写文章。只读这一个文件，不要 ls/grep/读其他文件。` +
      `不要输出计划或总结。写完只回一行：文件路径 | 有效字数。`,
      { label: it.id, phase: '写文章' }
    )
    return text ? { id: it.id, out: it.outPath } : null
  }))
  done.push(...got.filter(Boolean))
  log(`已完成 ${done.length}/${items.length}`)
}
return { count: done.length, done }
```

要点：

- `agent(prompt, opts?)` 返回子代理最终文本；失败返回 `null`（用 `.filter(Boolean)` 过滤）。
- `parallel(thunks)` 是屏障；多阶段彼此独立时优先 `pipeline(items, ...stages)`。
- hook 误用（参数错、未知选项、schema 不支持、触顶）会直接**杀掉整个脚本**，不会退化成 `null`。
- 脚本内没有文件系统/网络/定时器，只有 `agent` / `pipeline` / `parallel` / `phase` / `log` / `args`。
- 只有用户明确要求工作流或大型多 agent 编排时才用 `workflow`；一两项委派用普通 `subagent` 即可。

## 五、职责划分

| 角色 | 负责 |
|:--|:--|
| 主会话 | 变量组合决策、框架映射、写本轮事实卡与规范文件、生成任务书、跑确定性校验、小修小改、文档导入、汇总 |
| 子代理 | 只做彼此独立的"整篇产出"：生成一篇 prompt、生成一整篇文章 |

## 六、各步骤用不用子代理

| 步骤 | 用子代理？ | 说明 |
|:--|:--|:--|
| 0 项目初始化 | 否 | 全是确定性脚本 |
| 1 生文prompt生成 | 是 | 变量在主会话定死；子代理只写 prompt 文件、不跑校验 |
| 2 文章生成 | 是（成本大头） | 子代理只读任务书、只写文章文件 + 一行简报 |
| 3 审查校对 | **否** | 主会话跑校验脚本；小修 `edit`；超字数让代理回 cut list；只有整篇重写才复用原代理 |
| 4 文档导入 | 否 | 脚本与浏览器自动化 |

## 七、反模式（都是本轮踩过或差点踩的）

- ❌ 让子代理自检 / 跑校验脚本 —— 校验由主会话一次性跑全量，避免 N 份重复劳动和标准不一。
- ❌ 用子代理做"帮我 grep 一下""帮我看一眼"这类零碎活 —— 系统提示词与工具 schema 的固定开销纯亏，主会话自己做。
- ❌ 每个子代理各自解析 docx/xlsx —— 重材料先在主会话转成纯文本/事实卡。
- ❌ 小修新开代理重写整篇 —— 用 `edit` 或复用原代理。
- ❌ 把重材料读进**主会话**上下文 —— 主会话上下文是"每次调用都要背的前缀"（本轮平均 105k），同样计费。
- ❌ 为了省 input 而砍关键口径 —— 编造风险上升，返工代价远高于省下的 token。

## 八、验收指标

改完之后用这几个数验证（方法见 `references/成本模型与度量.md`）：

| 指标 | 本轮基线 | 目标 |
|:--|--:|--:|
| 文章子代理 ¥/个 | 0.42 | ≤ 0.15 |
| 每代理调用次数（3 篇） | 42 | ≤ 12 |
| 每次调用平均输出 token | 1,600 | ≤ 900 |
| 子代理合计（36 篇） | ¥6.94 | ≤ ¥2.5 |

同时必须抽查：文章结构合规率、字数区间、禁用词命中、六条备选标题——**成本降了但校验通过率掉了就是失败的优化**。
